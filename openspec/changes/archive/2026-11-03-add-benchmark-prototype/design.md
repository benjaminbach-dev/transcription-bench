# Design

## Context

Dépôt vierge hormis la mémoire projet (`.basic-memory/`) et un `.gitignore` excluant `data/`, audios, poids et environnements. Motivation : voir `proposal.md`. Exigences : voir les specs du change.

Hypothèses issues de la recherche documentaire du 2026-10-23 (notes `recherche/Moteurs et faisabilité technique` et suivantes), **non vérifiées par installation réelle** et donc documentaires :

- Plateformes visées : Windows x64 et Linux x64 (glibc ≥ 2.28). La recherche indiquait des roues cp312/abi3/py3 pour ces cibles ; les moteurs ont été installés et vérifiés sous Linux le 2026-11-01 ; sous Windows, aucune installation sur poste n'est prévue : la vérification passe par la CI (D14).
- Python 3.12 imposé de fait : PyAV 19 et numpy 2.5 exigeraient ≥ 3.12. Le serveur de développement (Debian 11, Python 3.9) passera par un Python géré par uv.
- Versions de référence : faster-whisper 1.2.1, ctranslate2 4.8.3 ; transcribe-cpp et transcribe-cpp-native 0.4.1 (épinglés ensemble, API pré-1.0) ; transformers 5.20.2, torch 2.14.1+cpu, librosa 1.0.0 (moteur Transformers, famille Parakeet) ; av 19.0.2 ; huggingface_hub 2.3.0 (le moteur Transformers en tire 2.4.0) ; psutil 7.2.2 ; uv 0.13.5 en référence documentaire, uv 0.11.8 étant la version réellement utilisée et validée sur le PC Linux de test (compilation du verrou, `--emit-find-links`, `--no-build`).
- Transformers n'offre pas d'inférence ASR générique : chaque famille a son parcours processor/generate/decode. Le premier jalon ne retient que Whisper et Parakeet TDT ; Qwen3-ASR, Voxtral, Cohere et Canary sont des extensions futures **via Transformers**, hors du périmètre de ce change (Qwen3-ASR est en revanche qualifiée via transcribe.cpp GGUF, tâche 8.2).
- Le serveur de développement ne télécharge ni moteur ni modèle. Il peut en revanche y installer les dépendances du serveur, pile web incluse (accord utilisateur explicite) et y développer et tester sans moteur réel : moteur factice, simulations et audios synthétiques locaux.
- Les essais du jalon 0 ont été exécutés sous Linux le 2026-11-01 (préparation des moteurs, imports, CPU, audios court et long — 47,7 s pour les quatre chemins, 300,9 s pour les deux familles Transformers —, hors ligne avec coupure réseau OS, et sonde web 1.7 sous Linux : 8 scénarios concluants, Ctrl+C par 0x03 sur le maître du PTY, limite d'un PTY automatisé et non d'une console humaine). Le jalon 0 Windows n'est plus un préalable : aucun PC Windows n'est disponible et les vérifications Windows sont remplacées par des exécutions réelles en CI (D14), dont les limites sont explicites. Le jalon 0 Linux acquis ne conditionne donc plus l'écriture des adaptateurs réels ; les choix de moteur, famille, fichiers et long-form restent ouverts tant qu'ils ne sont pas vérifiés. Les tests du serveur de développement ne valent pas validation Windows, et la CI ne vaut pas qualification sur le PC de l'utilisateur : ces preuves sont classées à des niveaux distincts (spec `platform-verification`).

## Goals / Non-Goals

**Goals:**
- Une couche web conventionnelle Flask/Jinja2, sans base de données, lisible et maintenable sans réinventer routage, parsing des formulaires ou rendu HTML.
- Des routes minces et un métier indépendant du framework ; un lancement local supervisé, sans rechargement automatique.
- Isolation stricte des dépendances de chaque moteur et du serveur.
- Mesures prises au plus près du moteur, dans des conditions consignées.
- Développement et tests possibles sans aucun moteur réel (moteur factice).
- Garanties vérifiables : inférence hors ligne, aucun code distant, installations conformes aux verrous, stockage atomique.
- Des preuves Windows réelles et reproductibles sans poste Windows, grâce à une CI dont les limites sont explicites.

**Non-Goals:**
- File d'attente d'opérations, multi-utilisateur, authentification.
- Conversion de modèles (CTranslate2, GGUF) : seuls les formats déjà publiés sont acceptés.
- Évaluation automatique de la qualité, diarisation, GPU, macOS.
- Diff textuel, score, texte de référence ou répétitions automatiques entre résultats.
- Familles Transformers autres que Whisper et Parakeet TDT.
- Qualification sur un PC Windows de l'utilisateur, garantie de performance sur PC, validation clinique.

## Decisions

### D1. Structure et lancement
Projet uv à la racine : `pyproject.toml` (`requires-python = ">=3.12"`), `.python-version` à 3.12, paquet `transcription_bench/`, script `transcription-bench`. Lancement : `uv run transcription-bench [--port N]`. uv crée l'environnement du serveur et télécharge si besoin un CPython géré. Dépendances directes du serveur : `flask==3.1.3`, `waitress==3.0.2`, `av`, `numpy`, `huggingface_hub`, `psutil`, avec leurs dépendances transitives (dont Jinja2 et Werkzeug) verrouillées par `uv.lock`. Flask 3.1.3 et Waitress 3.0.2 restent des versions de référence : leur installation et leur fonctionnement combinés sous Python 3.12 sont contrôlés sur le serveur de développement, puis par la sonde 1.7 sur PC.
Organisation minimale : point d'entrée CLI et supervision, module web avec fabrique `create_app(config, services)`, routes et dossier `templates/` contenant un gabarit de base et les pages `.html`. Pas de blueprints ni d'extensions ajoutés sans besoin. Le créneau d'opération, les moteurs et le stockage ne dépendent pas de Flask ; les routes valident la demande puis appellent ces services. La fabrique ne prend aucun verrou d'instance et ne démarre ni serveur ni thread, pour permettre les tests sans effets de bord.
*Alternative écartée* : script d'amorçage installant uv lui-même — accès réseau implicite et code spécifique par OS ; la documentation renvoie à l'installeur officiel.

### D2. Framework web, rendu et serveur local
**Flask + Jinja2 + Waitress** remplacent le serveur HTTP et le rendu HTML maison. Flask fournit routes GET/POST, `request.form`, réponses, redirections et client de test ; les templates Jinja2 `.html` bénéficient de l'échappement automatique de Flask. Aucun contenu externe n'est marqué `safe` ou `Markup`, et aucun template n'est construit à partir de saisies. Les formulaires restent `application/x-www-form-urlencoded`, avec POST → redirection 303 → GET après une action acceptée ; les refus sont des réponses 4xx. Pas de multipart, de session, de cookie, de `flash()` ni de Flask-WTF. Pages d'état avec lien « Actualiser ».

Waitress est lancé uniquement par l'API publique `waitress.serve(app, host="127.0.0.1", port=N, threads=4, max_request_body_size=1048576)` depuis la CLI, dans le thread principal, port par défaut 8765. Un seul processus serveur ; pas de `flask run`, `app.run`, débogueur, reloader, workers multiples ou configuration de proxy. L'application Flask désactive debug et la route statique par défaut (`static_folder=None`). L'URL affichée par notre CLI utilise `http://127.0.0.1:<port>` ; elle ne dépend pas des messages de journalisation de Waitress. Une erreur de liaison du port est signalée clairement et libère le verrou d'instance.

Un hook global `before_request` applique les protections avant tout effet de bord, dans l'ordre Host, Origin, type, taille puis jeton :
- En-tête `Host` comparé exactement à `127.0.0.1:<port>` ou `localhost:<port>` ; sinon 403, y compris sur les routes inexistantes. `TRUSTED_HOSTS` ne remplace pas ce contrôle : Werkzeug ignore le port dans sa validation native.
- POST : jeton anti-CSRF aléatoire propre à l'instance, renouvelé à chaque démarrage, injecté par le contexte des templates et recopié dans un champ caché. Vérification par `hmac.compare_digest`, sans cookie ni session ; `Origin`, s'il est présent, doit correspondre à l'une des origines HTTP locales autorisées avec le port, sinon 403 ; `Origin: null` est refusé.
- `MAX_CONTENT_LENGTH` fixe une limite applicative de 64 Kio ; dépassement refusé en 413 avant lancement d'une action. Seuls les formulaires urlencoded sont acceptés pour les POST ; les autres types sont refusés en 415. Waitress reçoit le corps entier avant d'appeler Flask : la limite Flask ne borne donc pas ce tampon. Le paramètre public `max_request_body_size` de Waitress le limite séparément à 1 Mio. Les requêtes rejetées par Waitress avant Flask (HTTP malformé, en-têtes ou corps au-delà des limites du serveur) reçoivent sa réponse propre, sans template et sans appel de l'application.
- Chemins contrôlés dans les services : tout nom d'audio ou de résultat est résolu puis vérifié comme restant sous le dossier autorisé (`data/audio`, `data/results`) ; traversée `..`, liens symboliques sortants et chemins absolus sont refusés. Identifiants de modèle validés par motif avant tout usage réseau ou fichier.

Les erreurs HTTP traitées par Flask, dont 404, 405, 413 et 415, et les erreurs inattendues 500 utilisent des templates HTML seuls, échappés, sans trace d'exception dans la réponse ; la trace reste dans le journal local. Les handlers conservent les codes et en-têtes HTTP applicables (notamment `Allow` pour 405). Aucun écran de debug interactif n'est accessible.

**Raison du choix :** conventions documentées et outillage commun pour chaque nouvelle page ; Jinja2 est proche de Twig et le modèle requête/réponse synchrone est familier en PHP. Waitress est pur Python, compatible Windows/Linux et recommandé parmi les serveurs de déploiement par Flask. Le serveur de développement Werkzeug n'est pas retenu : la documentation Flask déconseille son usage même pour une application privée locale.
*Alternatives écartées* : stdlib ou Jinja2 seul — routage, parsing, erreurs et client de test resteraient à entretenir ; Bottle — moins de conventions et pas de client de test intégré ; Django — configuration et briques inutilisées sans ORM, comptes ni administration ; Starlette/FastAPI/Litestar — ASGI et assemblage supplémentaires sans besoin d'API ou d'asynchrone ; CherryPy — pas de moteur de templates intégré. Flask ne dispense pas des contrôles spécifiques de chemins, d'origine ou de supervision des moteurs.

**Sources documentaires consultées le 2026-10-24 :** [installation Flask](https://flask.palletsprojects.com/en/stable/installation/), [templates](https://flask.palletsprojects.com/en/stable/templating/), [tests](https://flask.palletsprojects.com/en/stable/testing/), [déploiement](https://flask.palletsprojects.com/en/stable/deploying/), [API Waitress](https://docs.pylonsproject.org/projects/waitress/en/stable/api.html), [source Waitress 3.0.2](https://github.com/Pylons/waitress/tree/v3.0.2/src/waitress). Au 2026-10-24, aucune installation de cette pile n'avait été effectuée ; l'installation et les tests sur le serveur de développement sont autorisés. La sonde 1.7 a été exécutée depuis sous Linux (2026-11-01, 8 scénarios, Ctrl+C par PTY, preuves hors Git sous `data/feasibility/`) ; sous Windows, les points vérifiables sans console relèvent de la CI (D14) et la console interactive reste une limite consignée avec sa procédure (section 10 des tâches). Aucune de ces preuves n'est équivalente à une qualification PC Windows.

### D3. Créneau unique d'opération longue
Un objet `OperationSlot` protégé par verrou détient au plus une opération globale (installation, vérification distante, téléchargement ou exécution) exécutée dans un thread démon propre au projet, avec état, journal et horodatage. Ce thread ne dépend pas d'un contexte de requête Flask et ne reçoit pas les objets `request` ou `session` ; il reçoit des valeurs validées et les services nécessaires. Le passage à l'état d'arrêt et l'acceptation de toute mutation se font sous le même verrou du créneau : une opération acceptée avant ce passage est prise en charge par le nettoyage, toute demande ultérieure est refusée. L'écriture d'un marqueur « prêt » vérifie aussi cet état sous ce verrou pour qu'une opération encore active ne publie pas sa ressource pendant l'arrêt. Toute nouvelle demande est refusée si le créneau est occupé. Les vérifications distantes de compatibilité de modèle sont également refusées pendant une exécution. La règle du créneau global appartient à la spec `local-web-interface` ; la spec `benchmark-runs` ne décrit que la séquence des audios dans une exécution. Évite qu'un téléchargement fausse les mesures CPU d'une exécution, sans file d'attente.

### D4. Moteurs : adaptations, environnements et verrous
- Dossier `engines/` avec, par moteur, une **déclaration** (nom, fichier de dépendances, règles de compatibilité, familles, réglages exposés, durée native) et un adaptateur d'exécution. La déclaration est importable par le serveur sans aucune dépendance du moteur : elle ne fait que des imports de la bibliothèque standard et ne charge aucun paquet moteur.
- Le code d'exécution est chargé uniquement dans le processus du moteur, avec des imports différés à l'intérieur des fonctions (torch, faster_whisper, transcribe_cpp…), jamais à l'import du module serveur.
- Dépendances : `requirements/<moteur>.in` compilé en `requirements/<moteur>.txt` par `uv pip compile --universal`, versionnés. Installation : `uv venv --python 3.12 data/engines/<moteur>` puis `uv pip sync --no-build --python <interpréteur-du-venv> requirements/<moteur>.txt` ; `--no-build` évite toute compilation à l'installation. Le verrou Transformers est auto-porté et sans hashes : il porte `--find-links https://download.pytorch.org/whl/cpu/torch/`, émis par `--emit-find-links`.
- Un marqueur d'installation atomique n'est écrit et le moteur n'est marqué **prêt** qu'après : code de sortie 0 de l'installation, contrôle d'import réussi dans un sous-processus avec l'interpréteur du moteur, et synchronisation réussie par `uv pip sync` depuis le verrou applicable à l'OS. uv évalue les marqueurs : le programme ne réimplémente pas un comparateur de dépendances. Au redémarrage, un environnement sans marqueur est affiché en **échec**, jamais prêt et une nouvelle installation explicite rejoue `sync` puis le contrôle d'import. L'empreinte du verrou et la date d'installation sont consignées.
- Transformers : torch depuis l'index `https://download.pytorch.org/whl/cpu` sur les deux OS. Aucune affirmation sur l'absence de CUDA dans les roues : c'est le verrou et l'index qui fixent la variante, et le périphérique est imposé explicitement (D6). `librosa` 1.0.0 y est une dépendance obligatoire pour la famille Parakeet, avec ses transitives numba, llvmlite, scipy, soxr et soundfile. L'environnement du moteur Transformers définit `NUMBA_CACHE_DIR` sous `data/`, pour cantonner le cache JIT hors du profil utilisateur.
- Ajouter un moteur = une déclaration + un adaptateur + un `.in`/`.txt`, conformément à la spec.
*Alternative écartée* : un seul projet uv avec groupes en conflit — installation simultanée impossible et plus fragile pour des environnements créés à la demande.

### D5. Protocole serveur ↔ moteur
Pour chaque exécution, le serveur décode les audios (D7) en fichiers `float32` 16 kHz mono dans un dossier de travail sous `data/cache/<id>` (créé paresseusement au lancement, jamais au démarrage du serveur, puis supprimé à la fin), écrit un `job.json` (modèle, chemins, réglages, threads demandés), puis lance `data/engines/<moteur>/…/python engines/runner.py job.json` avec un environnement contrôlé. Les signaux décodés ne vont donc jamais dans le répertoire temporaire du système, que le programme ne maîtrise pas. Après un arrêt brutal du serveur, ces dossiers peuvent subsister : leur nettoyage relève de la clôture des exécutions abandonnées (D11, tâche 6.5). Le runner charge le modèle une fois, traite les audios un par un et émet des lignes JSON préfixées par un marqueur fixe (par exemple `##TB-EVENT## `). Le serveur n'interprète que les lignes portant ce marqueur et journalise les autres lignes stdout comme sortie parasite, sans échec ; un événement reçu deux fois (même index d'audio, second `chargement` ou second `fin`) est traité comme une ligne parasite, seul le premier étant conservé. stderr est conservé dans le journal de l'exécution. Le serveur est seul à écrire les résultats.
Durant une exécution, le moteur est lancé dans son propre groupe de processus (`start_new_session=True` sous Linux, `CREATE_NEW_PROCESS_GROUP` sous Windows) afin que Ctrl+C au terminal soit géré par la supervision du serveur sans course de finalisation avec le moteur ; l'environnement transmis fixe `HF_HUB_OFFLINE=1` et `PYTHONIOENCODING=utf-8`, le serveur décodant la sortie du moteur en UTF-8 quelle que soit la page de code de la console Windows.
Arrêt : à la demande de l'utilisateur ou à l'arrêt normal du serveur, le processus du moteur est terminé, les résultats déjà écrits sont conservés et l'exécution est marquée interrompue. Sous Linux, le signal vise le **groupe** (`SIGTERM`, attente bornée, puis `SIGKILL` si nécessaire), pour atteindre aussi les descendants lancés par le moteur ; la descendance est en outre relevée avec psutil (`children(recursive=True)`) **avant** le signal, puis attendue et tuée si elle y survit, un descendant insensible à `SIGTERM` restant sinon vivant après la sortie du processus principal. Sous Windows, faute d'équivalent portable de `killpg`, l'arrêt parcourt l'arborescence psutil et termine les enfants puis le parent : c'est un « au mieux » assumé, sans Job Object ni `CTRL_BREAK_EVENT`, et un descendant créé après ce parcours ou détaché de l'arborescence peut survivre. Si le processus survit à `kill`, l'interface l'indique et le créneau reste occupé jusqu'à sa fin réelle, avant la suppression du dossier de travail. Limite assumée : dès que le processus principal a disparu, son groupe n'est plus signalable (`os.getpgid` échoue) ; seuls les descendants relevés avant le signal peuvent encore être atteints, jamais ceux créés ensuite. Les audios non traités sont marqués comme tels. Le moteur factice est exécuté par le même runner avec l'interpréteur du serveur. Sa déclaration porte `factice=True` : ce drapeau, fixé par le code du dépôt et jamais par un job, autorise l'exécution de ses familles sans qualification PC et marque chaque événement (`factice`, `mesures_simulees`). Ce n'est pas une validation PC : aucune inférence réelle n'a lieu et les familles réelles ne sont exécutables qu'après leur qualification et leur implémentation ; Whisper pour les trois moteurs et Parakeet TDT pour Transformers sont désormais implémentés et vérifiés sur un court audio Linux. Pour qu'il soit proposable, le formulaire d'exécution ajoute à sa liste un modèle synthétique du moteur factice, sans inventaire ni fichier (clé constante, libellé « aucun modèle, textes et mesures simulés ») ; le job de la tâche 6.3 lui passera un chemin fictif sous `data/`, car `runner._modele` exige une chaîne de chemin non vide.

Arrêt normal du serveur = Ctrl+C sur les deux OS, et SIGTERM sous Linux. La CLI installe un même gestionnaire pour SIGINT et, sous Linux, SIGTERM : dès le premier signal, il remet ces signaux à `SIG_IGN`, puis lève `KeyboardInterrupt` (SIGINT) ou `SystemExit` (SIGTERM). Les signaux suivants sont donc ignorés pendant l'arrêt de Waitress comme pendant le nettoyage. L'appel public `waitress.serve()` est encadré par un `try/finally` de supervision ; que Waitress intercepte ou propage l'exception, le nettoyage applicatif est exécuté à la sortie de cet appel, sans API interne `create_server`, `close` ou `task_dispatcher`.
Le nettoyage idempotent passe le créneau à l'état d'arrêt sous son verrou, termine et collecte le moteur ou le sous-processus d'installation avec des délais bornés, puis attend le thread d'opération pendant un délai borné. Si ce thread est terminé, la clôture est enregistrée et le verrou d'instance est libéré en dernier. Sinon, le journal signale l'opération non close et le verrou reste détenu jusqu'à la fin réelle du processus ; un `run.json` resté `running` sera récupéré selon D11. Une installation ou un téléchargement interrompu reste non prêt. Aucun thread Python n'est tué. Un téléchargement dans le processus serveur peut encore attendre ses E/S et ses threads internes, même si le thread d'opération est démon : aucun délai global de sortie n'est garanti pendant un téléchargement. Les Ctrl+C suivants sont ignorés ; tuer le processus ou fermer la console pour forcer la sortie constitue un arrêt brutal relevant de D11. Ce nettoyage n'est jamais placé dans `teardown_appcontext`, appelé à la fin de chaque requête, ni dans un handler HTTP d'arrêt du serveur.
La source taggée Waitress 3.0.2 montre que sa boucle intercepte ces exceptions et demande la fin des threads de requêtes avec un délai de 5 s ; ces threads sont démons. Ce constat n'est pas une API d'arrêt sur laquelle l'application s'appuie : après retour de `serve()` et nettoyage applicatif, la CLI quitte le processus et le système ferme les sockets restants. Aucune relance du serveur dans ce même processus n'est prévue. Fermer brutalement la console Windows, Ctrl+Break sous Windows ou SIGHUP sous Linux relève de la récupération D11, pas de cet arrêt normal. Sous Linux, cet arrêt est éprouvé par la sonde 1.7 (`uv run`, Ctrl+C par 0x03 sur le maître du PTY, double Ctrl+C avec 83 signaux ignorés, SIGTERM sur le lanceur puis sur le serveur, absence de survivant, verrou libéré), avec la limite d'un PTY automatisé et non d'une console humaine avec frappe clavier. Sous Windows, la console interactive n'a pas été éprouvée : c'est une limite consignée, et l'annulation d'un job d'intégration continue n'est pas un arrêt normal et ne la remplace pas.

### D6. CPU uniquement et threads
| Moteur | CPU | Threads | Vérification |
|---|---|---|---|
| faster-whisper | `device="cpu"` | `cpu_threads=N` | implicite (périphérique imposé, aucun repli GPU) |
| transcribe.cpp | `TRANSCRIBE_BACKENDS=cpu` + `backend="cpu"` | `model.session(n_threads=N)` | `model.backend.casefold() == "cpu"`, sinon erreur ; la version 0.4.1 renvoie `"CPU"` sur le PC Linux validé, la valeur brute reste consignée |
| Transformers | `CUDA_VISIBLE_DEVICES=""`, modèle sur `cpu` | `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `torch.set_num_threads(N)` avant tout calcul | `torch.get_num_threads()` consigné, si l'API est disponible |

Le nombre de threads demandé et, lorsque l'API permet de le lire, le nombre appliqué sont consignés séparément ; sans API de lecture, seul le demandé est consigné et aucun appliqué n'est affirmé. Valeur par défaut : nombre de cœurs physiques (`psutil.cpu_count(logical=False)`), à défaut cœurs logiques.

### D7. Décodage audio commun
PyAV (FFmpeg embarqué dans ses roues) dans l'environnement du serveur : décodage, mixage mono et rééchantillonnage 16 kHz `float32`. Empreinte SHA-256 du fichier source. La durée affichée dans la liste des audios est **indicative** ; la durée de référence, utilisée pour le RTF, est la durée décodée (nombre d'échantillons / 16 000) et les deux sont consignées. Le découpage en fenêtres s'applique audio par audio. Le cache décodé est supprimé à la fin de l'exécution.

### D8. Mesures
Dans le runner : `time.perf_counter()` pour le chargement et la transcription, `time.process_time()` (tous threads du processus) pour le temps CPU, pic de mémoire résidente du processus depuis son démarrage (`resource.getrusage().ru_maxrss` en Kio sous Linux ; `psutil.Process().memory_info().peak_wset` sous Windows avec psutil 7.2). Pic relevé après chargement puis après chaque audio (valeur cumulative) ; pic final à la fin normale de l'exécution. Pour une interruption ou un échec, le pic disponible est le dernier relevé transmis, signalé comme incomplet ; les durées sont mesurées jusqu'à la clôture et la sortie du moteur. Pour une exécution abandonnée, les durées totale et du processus sont inconnues et le dernier pic transmis reste identifié comme partiel. Les mesures indisponibles sont affichées comme absentes, jamais comme zéro.
Le serveur mesure séparément le temps de décodage par audio et la **durée totale de l'opération**, du début de sa préparation à la fin de la collecte du moteur et de l'écriture des résultats d'audios, décodage, chargement, inférence et écriture compris (hors ultime sauvegarde de `run.json`) ; la **durée du processus moteur**, du lancement à sa sortie, est consignée séparément. Le RTF est calculé sur la durée décodée ; une durée décodée nulle est une erreur et aucun RTF n'est calculé. transcribe.cpp : mode mmap par défaut consigné et `Result.timings` conservés dans le champ facultatif `timings_natifs`, distinct des réglages effectifs stables. Une entrée par appel garde l'unité `ms` rapportée par transcribe.cpp 0.4.1 et ses champs `load_ms`, `mel_ms`, `encode_ms`, `decode_ms`, sans somme ni conversion. Les entrées suivent l'ordre des fenêtres ; les valeurs absentes/non finies restent indisponibles, jamais inventées à zéro. Ce chemin a été vérifié par HTTP Linux en appel natif et en deux fenêtres de 30 s ; la tâche 8.2 reste ouverte uniquement pour la seconde architecture GGUF.
Le moteur factice n'utilise pas ces mesures : le runner émet à leur place des valeurs simulées déterministes et constantes, marquées dans chaque événement par `factice=True` et `mesures_simulees=True` ; seule la durée décodée de l'audio reste réelle. Ces valeurs servent à exercer le protocole et ne sont jamais présentées comme représentatives d'un PC.

### D9. Audios longs et fenêtres de secours
Chaque adaptateur déclare, par famille, la durée native maximale et la méthode retenue. Au 2026-11-01, la durée maximale prouvée sur le PC Linux de test (30 Gio de RAM) est de **5 min** pour les deux familles Transformers, sous le plafond de 12 Gio : pic RSS de 5112 Mio pour Whisper turbo, atteint dès le chargement (RSS échantillonné ~3787 Mio pendant la transcription de 5 min) ; 4915 Mio pour Parakeet, dont ~1041 Mio au chargement et le reste amené par la passe longue ; au-delà, rien n'est prouvé. Sans mécanisme natif prouvé, le runner découpe l'audio en fenêtres fixes de **30 s** sans recouvrement, concatène les textes et décale les horodatages éventuels ; la durée de fenêtre effective est consignée **pour chaque audio**.
- Transformers Whisper : long-form natif confirmé jusqu'à 300,9 s (RTF proche à 47,7 s et 300,9 s : 0,515 et 0,494 ; fenêtres internes de 30 s du modèle). La troncature silencieuse à 30 s est **interdite** : l'appel de processor par défaut tronque sans erreur, donc les paramètres `truncation=False`, `padding="longest"` et `return_attention_mask=True` sont fixés, et l'adaptateur vérifie que le nombre de trames mel couvre la durée décodée (l'axe des trames dépend de la famille : `[1,128,T]` pour Whisper, `[1,T,128]` pour Parakeet). Fenêtres fixes de 30 s seulement en repli non natif.
- Transformers Parakeet TDT : natif en une passe jusqu'à la durée maximale prouvée et consignée (5 min au 2026-11-01) ; fenêtres fixes de 30 s au-delà, ou si la durée native n'est pas prouvée pour la famille. Le RTF est plus élevé à 300,9 s qu'à 47,7 s (0,102 et 0,186 ; trois points non monotones, chaque mesure en un seul passage) — explication probable, lue dans le code installé et non mesurée : attention non fenêtrée. Le RTF reste consigné.
- faster-whisper et transcribe.cpp : famille disponible seulement après vérification de son architecture (Whisper au jalon 0, autres architectures transcribe.cpp en tâche 8.2). Pour une architecture vérifiée, mécanisme long natif s'il est vérifié lui aussi, fenêtres fixes sinon. Une architecture non vérifiée reste refusée à l'ajout.
Le découpage commun pour toutes les familles est écarté pour le prototype : il mesurerait notre découpage plutôt que le comportement des moteurs.
Le mécanisme de long-form est commun aux deux OS : aucune règle par OS n'est introduite. L'incertitude porte sur la mémoire disponible de la machine, pas sur l'OS — les 5 min ont été prouvées sur un PC Linux de 30 Gio de RAM —, d'où le risque de bascule vers les fenêtres de 30 s sur un PC moins doté (section Risks) ; la CI ne prouve pas de comportement long-form.

### D10. Modèles Hugging Face, hors ligne et sans code distant
Dans le serveur, via huggingface_hub (jeton lu par ses moyens standards, jamais stocké) :
- `HfApi.model_info(id, revision, files_metadata=True)` : commit exact et taille des fichiers.
- Pour Transformers : lecture des petits JSON de configuration attendus (`config.json`, `processor_config.json` ou `preprocessor_config.json`, `tokenizer_config.json` et, selon la famille, `generation_config.json`), `model_type` comparé aux familles vérifiées de l'adaptateur, puis sélection d'une **liste blanche de fichiers suffisante par famille** : poids safetensors et index/shards éventuels, configuration du modèle, du processor/préprocesseur, `generation_config.json` — **requis** pour Parakeet TDT, dont l'absence fait échouer `generate()` (`decoder_start_token_id` nul) —, vocabulaire/tokenizer et éventuels fichiers de fusion. Profil strict retenu pour le prototype, à confirmer au jalon 0 : `tokenizer.json` et `tokenizer_config.json` sont requis pour chaque famille ; un tokenizer fourni seulement en `vocab.json` et `merges.txt` est refusé comme incomplet, bien que Transformers sache le lire. Aucun mode de repli sur ce vocabulaire réduit n'est prévu : ce choix de simplicité diminue les variantes à couvrir ; ses limites restent soumises à validation PC. Parakeet peut utiliser `processor_config.json`, pas nécessairement `preprocessor_config.json`. Un `auto_map` dans l'un des JSON de configuration inspectés est un motif de refus, mais le programme ne prétend pas qu'un simple scan de `auto_map` suffit : la décision repose sur la liste de fichiers et le type de modèle déclarés, et seuls les poids safetensors sont sélectionnés et chargés (`use_safetensors=True` aux API concernées). Tous les fichiers hors de la liste blanche, notamment variantes pickle, `.nemo`, `.gguf`, `.onnx` ou `.h5`, sont ignorés pour Transformers ; un dépôt sans variante safetensors complète est refusé.
- faster-whisper : présence de `model.bin`, `config.json`, `tokenizer.json`, `preprocessor_config.json` et des fichiers de vocabulaire facultatifs (`vocabulary.json` ou `vocabulary.txt`). `preprocessor_config.json` est requis pour tous les points de contrôle CTranslate2 Whisper, y compris `Systran/faster-whisper-small`, sans repli sur les valeurs par défaut de la bibliothèque ; ce profil strict, retenu pour réduire les variantes, reste à confirmer au jalon 0, qui vérifie aussi l'absence de repli vers un tokenizer distant.
- transcribe.cpp : liste des `*.gguf` ; lecture partielle de l'en-tête du fichier choisi via `HfFileSystem` pour extraire `general.architecture`, comparée aux architectures prises en charge par la version épinglée. Un GGUF repéré comme fragment par son nom (`-00001-of-00002.gguf`) est refusé avant tout téléchargement et ne peut jamais devenir prêt : une seule variante autonome est prise en charge. Cette détection par nom ne prouve ni l'intégrité intrinsèque du fichier ni l'absence d'un renommage malveillant ; elle ne constitue pas une prise en charge des modèles découpés.
- Téléchargement : `snapshot_download(id_resolu, revision=<commit>, allow_patterns=[glob.escape(nom)…], local_dir=data/models/<moteur>/<CLE>/fichiers, max_workers=1)`. `<CLE>` est le SHA-256 d'un encodage JSON déterministe de `[id_resolu, commit, fichier_gguf ou null]` : l'identifiant n'est ni transformé en `<org>__<nom>` ni utilisé comme nom de dossier, ce qui évite la collision relevée en 3.3 et donne une clé distincte à chaque variante GGUF. Tous les identifiants acceptés par la vérification restent valides, y compris un nom seul ou un nom réservé Windows, sans créer de dossier réservé. `model.json`, écrit atomiquement seulement après succès, porte le nom demandé, l'identifiant canonique, le commit exact, la famille, la variante GGUF et les fichiers retenus avec leur taille connue ; à la lecture, la clé est recalculée et comparée au dossier et au manifeste, si bien qu'un manifeste incohérent, illisible ou absent n'est jamais prêt. Le sous-dossier `fichiers/` sépare les fichiers téléchargés de l'inventaire, qu'un fichier distant autorisé nommé `model.json` ne peut donc pas remplacer. Une nouvelle demande explicite peut compléter un dossier partiel, sans écraser une autre variante ni un modèle déjà prêt.
- Le téléchargement reprend uniquement l'identité du dernier résultat de vérification accepté (moteur, identifiant canonique, commit, variante GGUF et fichiers retenus côté serveur). Les champs du formulaire ne fournissent ni commit, ni liste de fichiers, ni verdict : seule une empreinte du dernier résultat permet de refuser une page périmée ou modifiée, sans nouvelle authentification ni session.
- Inférence et exécution du moteur : `HF_HUB_OFFLINE=1` obligatoire, `local_files_only=True` lorsque l'API du moteur le permet, `trust_remote_code=False` aux API qui exposent cette option. Aucun accès réseau une fois les fichiers présents.

### D11. Stockage des résultats, atomicité et clôture après incident
Fichiers JSON et texte, sans base de données :
```
data/results/<AAAAMMJJ-HHMMSS>-<court-id>/
  run.json        configuration, modèle, moteur, versions, machine, état, ordre des audios, mesures globales
  run.log         journal stderr du moteur
  <n>-<nom-audio>/
    transcription.txt
    result.json   audio (nom, SHA-256, durée indicative et décodée, format), segments, mesures, erreur éventuelle
```
Écriture atomique : chaque JSON est écrit dans un fichier temporaire du même dossier puis remplacé par `os.replace`, afin qu'une interruption de processus ne laisse pas un JSON tronqué. Un verrou serveur commun protège les lectures et remplacements JSON afin de ne pas tenter un remplacement Windows pendant une lecture ; ce comportement sera exercé sous Windows par la suite de tests en CI (D14). Un résultat d'audio est écrit avant de passer au suivant.
Une erreur d'écriture (disque plein, droits, remplacement refusé) est retenue, elle n'est jamais avalée : le moteur est arrêté aussitôt et la collecte s'arrête, les résultats déjà écrits restant valides. Le cache décodé de l'exécution est supprimé avant la clôture pour libérer de la place, et l'état final est **toujours tenté**, en `failed` avec le motif retenu. Seule une ultime écriture qui échouerait aussi laisse `run.json` dans son état précédent (`running`) : la récupération de 6.5 le finalise alors en `abandoned`. Le PID et l'heure de création du processus moteur sont consignés dans `run.json` dès son lancement ; si cette écriture échoue, le moteur est arrêté et l'exécution conclut en échec avant toute collecte, plutôt que de continuer sans PID persisté. `run.json` évolue pendant l'exécution (état `running`, progression), puis devient immuable une fois l'état final atteint (`completed`, `interrupted`, `failed`, `abandoned`). Une seule instance du serveur peut utiliser le même dossier de données (verrou de fichier d'instance détenu par le système et libéré automatiquement à la mort du processus, y compris après arrêt brutal ; primitive vérifiée sous Linux ; son comportement sous Windows sera exercé par la suite de tests en CI (D14)) : un démarrage concurrent est refusé avant toute récupération. Un simple fichier de PID persistant ne constitue pas ce verrou. La CLI prend ce verrou et termine la récupération avant de construire l'application et d'appeler Waitress ; aucune route ne peut donc accéder à un état en cours de récupération. Au redémarrage après un arrêt brutal, le serveur termine le moteur encore vivant seulement si son PID et son heure de création concordent, puis toute exécution restée `running` est finalisée automatiquement en `abandoned`, ses audios sans résultat étant signalés non traités ; les restes de `data/cache/` sont ensuite supprimés, aucun moteur enregistré n'étant plus vivant. Seuls les dossiers de travail d'exécutions (préfixe `execution-`) sont purgés, jamais un autre contenu déposé dans `cache`, et jamais à travers un `cache` qui serait un lien symbolique ou une jonction. Il n'y a pas de reprise d'inférence dans une ancienne exécution : retranscrire les audios restants crée une nouvelle exécution, avec un nouveau chargement et de nouvelles mesures. La suppression d'un modèle utilisé par une exécution active est refusée.
Les pages de résultats et de comparaison relisent ces fichiers ; la comparaison regroupe par SHA-256.

Format effectif (tâche 6.4), versionné par le champ `schema` valant `1` dans `run.json` comme dans chaque `result.json` : une valeur inconnue doit être refusée par 6.5 et 7.x plutôt qu'interprétée. Les clés sont toujours présentes et une valeur indisponible vaut `null`, jamais zéro ; une mesure non finie (NaN, infini) est traitée comme indisponible.
- `run.json` : `schema`, `identifiant`, `etat` (`running`, puis `completed`, `interrupted`, `failed` ou `abandoned`), `cree_le`, `fin`, `erreur`, `factice`, `synthetique`, `mesures_simulees`, `demande` (moteur, famille, modèle avec identifiant/canonique/commit/clé/variante GGUF, audios dans l'ordre, threads demandés, réglages validés défauts compris, fenêtre fixe), `moteur` (identifiant, nom, `factice`, empreinte du verrou de dépendances du moteur, versions relues), `machine`, `programme` (version, Python, empreinte du `uv.lock` du serveur, PyAV et bibliothèques FFmpeg ; le commit du programme n'est pas consigné), `processus_moteur` (`pid`, `heure_creation`, `heure_creation_source` valant `psutil` ou `serveur`, `lance_a`, `code_sortie`), `effectifs` (threads demandés et, si le moteur les relit, appliqués ; réglages effectifs du dernier audio traité, absents sinon), `mesures` (`duree_operation_s`, `duree_processus_s`, `duree_chargement_s`, `pic_memoire_octets`, `pic_memoire_partiel`), `progression` (`audios_traites`, `audios_total`) et `audios` (par audio : `ordre`, `nom`, `dossier`, `statut` valant `ok`, `erreur` ou `non_traite`, `erreur`, `fenetre_s`, `decoupage`). `pic_memoire_partiel` vaut `null` sans aucun relevé, sinon `true` dès que le dernier pic ne vient pas de l'événement `fin` ou que l'exécution n'est pas terminée : un pic encore transmis par un audio n'est jamais présenté comme le pic final. La clôture en `abandoned` (6.5) renseigne `fin`, met `duree_operation_s` et `duree_processus_s` à `null` (jamais mesurées puisque le serveur est mort avant), conserve `duree_chargement_s` et le dernier `pic_memoire_octets` en le marquant partiel, recalcule `progression`, garde les statuts d'audios déjà consignés et marque `non_traite` tout audio sans `result.json` exploitable ; elle laisse `erreur` et `processus_moteur` inchangés et ne réécrit ni `result.json`, ni `transcription.txt`, ni `run.log`.
- `result.json` : `schema`, `execution`, `ordre`, `nom`, `dossier`, `statut`, `ecrit_le`, marques `factice`/`synthetique`/`mesures_simulees`, `audio` (nom, format, taille, SHA-256, durées indicative et décodée, échantillons), `modele` (identifiant, canonique, commit, clé, variante GGUF et famille), `moteur`, `machine`, `programme`, `reglages` (validés, défauts compris), `reglages_effectifs`, `timings_natifs` (facultatif pour les résultats antérieurs ; liste par appel avec unité, sans agrégation, ou `null`), `langue_imposee`, `threads` (demandés/appliqués), `fenetre` (durée, découpage, nombre de fenêtres), `mesures` (temps de décodage serveur, durée de transcription, temps CPU, RTF sur durée décodée, pic mémoire cumulatif transmis), `transcription` (texte, segments) et `erreur`.
- Nommage: `data/results/<AAAAMMJJ-HHMMSS>-<8 hexadécimaux>` créé exclusivement sous le verrou de stockage, jamais réutilisé ; dossier d'audio `<ordre 1-based>-<nom réduit à une composante portable>`, les caractères interdits (séparateurs, `:`, jokers, guillemets, contrôles) étant remplacés et les espaces/points finaux retirés, le préfixe d'ordre garantissant l'unicité et écartant les noms de périphériques réservés Windows. `run.log` reçoit toute la sortie d'erreur du moteur, sans borne ; une erreur d'écriture de ce journal est retenue à part et signalée dans le journal de l'opération, sans empêcher l'écriture des résultats. Les chemins persistés comme données sont relatifs au dossier de résultat : ni chemin absolu, ni secret ; seuls un message d'erreur d'E/S et les lignes brutes de `run.log` peuvent citer un chemin absolu du système.
- `heure_creation` est l'horodatage epoch brut (flottant, sans troncature à la seconde) attribué par le système au processus, lu par psutil ; il vaut `null` quand il n'a pas pu être lu, `heure_creation_source` valant alors `serveur`. `lance_a` vient de l'horloge du serveur, les deux pouvant différer de quelques dixièmes de seconde.
- **Règle d'identification du processus survivant (tâche 6.5)** : le processus enregistré n'est arrêté que si son heure de création lue par le système concorde avec une référence consignée. Source `psutil` et heure non nulle : comparaison directe avec `heure_creation`, tolérance de 1 s (même horloge système des deux côtés, résolution de psutil de 1/100 s). Source `serveur`, heure nulle ou absente : repli sur `lance_a`, tolérance de 5 s, plus large parce que `lance_a` est tronquée à la seconde et que l'horloge du serveur peut être décalée — environ 0,9 s d'écart relevé sur le serveur de développement. Une heure consignée non finie (NaN, infini) est traitée comme incohérente, et le PID du serveur lui-même n'est jamais visé. Hors tolérance, le PID désigne un autre programme et n'est jamais tué. La terminaison se fait en deux étapes bornées (`terminate`, attente, puis `kill`), sur le processus vérifié puis sur sa descendance psutil ; l'heure de création n'est pas relue par nos soins (`psutil.Process` la met en cache) : c'est la revérification interne de psutil 7.2.2 qui s'applique juste avant chaque signal (`is_running()` puis refus du signal si le PID a été réutilisé). Un processus inaccessible, non identifiable ou survivant à `kill` refuse le démarrage avec un message explicite plutôt que de clôturer une exécution dont le moteur vivrait encore ; une erreur système inattendue pendant cette étape refuse aussi le démarrage, sans trace Python. Une exécution finale n'est jamais modifiée ; le refus pour `run.json` illisible, d'un `schema` inconnu ou incohérent ne vaut que pour les exécutions `running`, les seules interprétées, et le fichier n'est pas réécrit ; un dossier de résultats sans `run.json` est ignoré. Chaque exécution traitée laisse une ligne de journal sur la sortie d'erreur (« PID n ignoré : identité différente », « moteur PID n terminé », « exécution X close en abandonnée »), sans secret. La récupération est idempotente.
- **Limites assumées de cette identification (tâche 6.5, sans code supplémentaire)** : une dérive d'horloge d'au moins 1 s entre l'horodatage consigné et l'horloge système fait prendre le moteur survivant pour un autre programme ; il n'est alors pas tué et la récupération clôt l'exécution, mais le moteur mourra à sa prochaine écriture, la tuyauterie du serveur étant fermée. Un arrêt brutal entre le lancement du moteur et l'écriture du PID dans `run.json` laisse un moteur non enregistré, donc non récupérable : il n'est ni terminé au redémarrage, ni signalé. La supervision des descendants orphelins pendant qu'une exécution est vivante relève de la tâche 6.6, réalisée : la supervision d'arrêt relève la descendance du moteur avant de signaler son groupe, attend puis tue les survivants. Cette protection ne couvre pas un descendant déjà orphelin après la sortie du processus principal (le groupe n'est alors plus signalable), ni un arrêt brutal : il n'est pas récupéré au redémarrage.

### D12. Tests et développement sur le serveur
Tests `unittest` limités aux parties à risque : règles de compatibilité (listes de fichiers et `config.json` d'exemple, dont refus d'un poids non safetensors pour Transformers, acceptation du `model.bin` CTranslate2, dépôts mixtes, et refus d'un `auto_map`), lecteur d'en-tête GGUF, stockage sans écrasement et écriture atomique, événements runner avec lignes stdout parasites, couche web via le client de test Flask utilisé depuis `unittest` (base URL locale avec le port attendu, contrôle `Host` et `Origin`, jeton anti-CSRF, formulaires urlencoded, limite 413, chemins refusés, absence de cookie, échappement de contenus externes, pages normales et d'erreur sans CSS/JS, mode debug désactivé), clôture d'une exécution abandonnée, protocole runner et supervision d'arrêt avec moteur factice. Les tests de pages 500 désactivent explicitement la propagation des exceptions pour exercer le handler. Ni pytest, ni httpx ni extension de formulaire ne sont nécessaires. Aucun test ne télécharge de moteur ou de modèle, ni n'appelle le réseau externe (le bouclage local reste autorisé pour les sondes), ni ne lit d'audio personnel : les audios de test sont générés localement. La même suite est destinée à tourner sous Linux et dans la CI Windows (D14), sans que cela vaille qualification PC. Les adaptateurs réels sont validés sous Linux sur le PC de test, puis sous Windows par la CI ; la qualification sur le PC de l'utilisateur n'est pas acquise.

### D13. Contraintes de l'adaptateur Transformers
Constats du jalon 0 (Linux, 2026-11-01) que l'adaptateur de la tâche 8.3 doit tenir :
- **dtype fp32 explicite**, consigné dans les réglages effectifs : `from_pretrained` prend `dtype="auto"` par défaut dans transformers 5.20.2, donc Whisper serait chargé dans son dtype de publication (fp16) — c'est précisément pour cela que fp32 doit être imposé sur CPU. Le comportement en fp16 n'a pas été mesuré.
- **`do_normalize` fixé explicitement** (`False` retenu et consigné pour Whisper lors de l'implémentation du 2026-11-02 ; aucun effet observé au jalon 0 sur l'audio court synthétique testé), sans dépendre de la valeur par défaut du processor.
- **`max_length` borné explicitement** pour Parakeet TDT : l'arrêt normal de la génération vient du critère d'épuisement de l'encodeur, pas du `max_length` générique (non atteint à 300,9 s) ; une borne explicite ne doit jamais tronquer un audio long — proportionnelle au nombre de trames encodeur, et son atteinte doit être détectée.
- **Langue Parakeet TDT** : l'API TDT utilisée ne reçoit aucune option de langue forcée ; le modèle reste multilingue et `langue_imposee` vaut `null`, contrairement à Whisper qui reçoit réellement `language="fr"`. Une transcription en français ne vaut pas preuve de langue imposée.
- **Horodatages Parakeet TDT** : durées cumulées par jeton (dernier horodatage à 99,92 % de la durée décodée) ; la segmentation affichée est une convention de lecture, pas une frontière acoustique mesurée.

### D14. Intégration continue pour les vérifications Windows
Aucun PC Windows n'étant disponible, la vérification sous Windows passe par des exécutions réelles en intégration continue, avec des limites explicites ; elle ne remplace ni la qualification sur le PC de l'utilisateur ni une mesure de performance.
- Hébergement : GitHub Actions, dépôt rendu public après audit (D15). Runners standards hébergés uniquement, sans runner plus grand ni payant : sur dépôt public, Windows x64 dispose de 4 vCPU, 16 Go de RAM et 14 Go de disque SSD ; sur dépôt privé, de 2 vCPU, 8 Go et 14 Go, avec consommation du quota de minutes du compte (multiplicateur Windows) — documentation GitHub consultée le 2026-11-02. Ce coût motive l'ordre « audit → publication → jobs Windows ». Un repli sur la CI d'un dépôt privé n'est pas décidé : ce serait un choix explicite de l'utilisateur.
- Image explicitement versionnée : libellé `windows-2022` ou `windows-2025`, jamais `windows-latest` qui suit l'image courante (Server 2025 au 2026-11-02). La version d'image relevée dans le journal du run est consignée avec le commit testé ; un changement d'image est traité comme un changement de preuve, pas comme une régression silencieuse.
- Sécurité de la configuration : `permissions: contents: read` par défaut et aucune permission d'écriture ; toutes les actions épinglées par SHA de commit complet, y compris les actions officielles `actions/*`, jamais par tag mobile ; cache de `setup-uv` (ou équivalent) explicitement désactivé ; aucun secret, aucun audio personnel ; audio de parole synthétique créé par le job et jamais versionné ; poids, audios, environnements et transcriptions jamais publiés en artéfact ni mis en cache par défaut ; `timeout-minutes` par job et `concurrency` avec annulation des exécutions obsolètes. Aucun dépôt de modèle exigeant un jeton n'est présumé accessible : si un dépôt retenu devient restreint, la combinaison est consignée comme non vérifiable en CI sans secret, et n'est ni contournée ni silencieusement sautée.
- Jobs, dans cet ordre : (1) suite `unittest` avec moteur factice sous Linux et Windows, qui exerce aussi le remplacement atomique des JSON et la protection des lectures/écritures ; (2) faisabilité d'un audio de parole synthétique local sur le runner Windows, hors ligne et sans dépendance ajoutée (SAPI non présumé disponible), préalable aux jobs d'inférence : si aucune voie locale fiable n'existe, la question remonte pour arbitrage explicite et le critère de transcription non vide n'est ni remplacé par du bruit ni affaibli en silence ; (3) un job Windows par moteur qui installe depuis les verrous avec `uv pip sync --no-build`, contrôle l'import puis exerce le runner du projet et l'adaptateur, sans cache de poids ; (4) un job Windows indépendant par combinaison d'inférence courte (faster-whisper, transcribe.cpp GGUF Whisper, Transformers Whisper, Transformers Parakeet TDT) sur l'audio de parole de (2), chaque job ne téléchargeant que son modèle et n'en gardant aucun cache, le disque du runner étant partagé avec l'OS ; (5) les combinaisons lourdes sont déclenchables manuellement (`workflow_dispatch`), l'automatique pouvant se limiter aux tests. Les modèles utilisés sont ceux déjà arrêtés en 1.1 : la CI n'introduit aucun modèle.
- La parole de test n'exige pas de voix française : une voix système activée suffit. Le harnais choisit de façon déterministe une voix anglaise, sinon française, sinon la première disponible, avec texte anglais ou français et éventuelle différence de langue consignée. Culture de voix, langue du texte et langue réellement imposée par le moteur sont distinctes ; les réglages fonctionnels de l'application ne sont pas modifiés pour le test. Le texte non vide est un contrôle de fonctionnement sans mot attendu ni évaluation du modèle ; une sortie vide rend le contrôle non concluant, pas un diagnostic de qualité.
- Preuves : commit SHA, libellé et version d'image, Python et uv, versions installées des moteurs, nature, procédure, culture de voix, langue du texte, langue imposée par le moteur et empreinte vérifiée de l'audio de parole, journaux des jobs et ressources mesurées (vCPU, RAM, disque). Elles sont classées au niveau « CI Windows » (spec `platform-verification`).
- Ce que la CI ne prouve pas : la qualification sur le PC Windows de l'utilisateur, une performance représentative (vCPU virtualisés partagés), l'arrêt interactif Ctrl+C simple et double dans une console Windows via `uv run`, ni une coupure réseau réelle du système. Les jobs n'exercent que les options hors ligne (`HF_HUB_OFFLINE`, `local_files_only`, `trust_remote_code`) et l'absence de téléchargement implicite : cela ne prouve pas l'absence d'accès réseau, et une sonde d'intégration continue dédiée à l'isolation réseau pourra être ajoutée après revue, sans valoir preuve de coupure OS. L'annulation d'un job n'est pas un arrêt normal : elle ne vaut pas vérification de la supervision. Ces points sont consignés comme limites avec leur procédure de levée.
- Aucun échec n'est contourné : pas de `continue-on-error` ni de saut conditionnel sur une combinaison. Un échec d'installation ou d'inférence sous Windows échoue le job et remonte à l'utilisateur pour décision (par exemple une roue absente), sans réduire silencieusement le périmètre des moteurs, des familles ou des modèles. Si la CI s'avère impossible ou si une combinaison échoue durablement, l'état est consigné comme bloqué ou partiel et une révision du périmètre relève d'une décision explicite de l'utilisateur : aucune clôture ni archivage automatique, et une livraison partielle n'est jamais présentée comme complète.

### D15. Audit préalable et publication du dépôt
Un premier audit en lecture seule a été produit le 2026-11-02 (`docs/audits/publication-2026-11-02.md`, non versionné à ce jour) avec un verdict défavorable à la publication : contexte d'un tiers dans la mémoire, versions historiques de notes non auditables par le MCP, exposition du contexte personnel et des identités d'auteur, absence de régime de licence choisi (une licence propriétaire, sans licence ouverte, reste une option), et nécessité d'un audit final du candidat réellement publié. Ces points restent ouverts ; aucun changement de visibilité n'est effectué par cette révision. Le rapport sera remis en forme par le porteur du projet ; il n'est pas modifié ici.
Le dépôt ne devient public qu'après un audit consigné : contenu et historique Git (secrets, jetons, données personnelles, poids, audios, environnements), contenu de la mémoire projet versionnée (`.basic-memory/`), licences du code et des dépendances, licences et conditions d'accès des modèles effectivement téléchargés par les jobs CI (contrôle ciblé, sans obligation d'attribution globale).
- La décision de publier est explicite, prise par l'utilisateur après lecture de l'audit. Un point non résolu (secret dans l'historique, donnée personnelle, licence incompatible) bloque la publication et donc l'exécution des jobs Windows sur runner public ; une remédiation d'historique (réécriture, rotation) relève d'un accord explicite distinct, hors de cette révision.
- La publication n'exige aucun secret supplémentaire : les jobs n'utilisent que des dépôts publics ; un dépôt restreint rend la combinaison correspondante non vérifiable en CI, cas consigné et non contourné.
- La CI elle-même reste à implémenter après cette révision : ni workflow, ni code, ni README, ni `AGENTS.md` ne sont modifiés ici.
*Alternative écartée* : activer les jobs Windows sur un dépôt privé avant audit — consommation de minutes et décision de visibilité prise de fait sans audit ; le dépôt est déjà hébergé chez le fournisseur, c'est le passage au public qui change l'exposition. Une CI privée reste possible mais n'est pas un repli décidé.

## Risks / Trade-offs

- [Versions et roues issues d'une recherche documentaire, non installées] → jalon 0 de faisabilité exécuté sous Linux (fait le 2026-11-01) et vérifications sous Windows par la CI (D14) ; une roue absente ou un import en échec sous Windows reste un écart à traiter avant de présenter la livraison Windows comme faite, sans bloquer les adaptateurs sous Linux.
- [Tests serveur ou code factice pris pour une validation PC] → développement et tests limités au moteur factice, aux simulations et aux audios synthétiques locaux ; les vérifications CI sont classées à leur propre niveau, aucune coche ne vaut qualification du PC de l'utilisateur, et les limites hors CI (console Windows, coupure réseau réelle) sont consignées avec leur procédure plutôt que présentées comme réalisées.
- [Long-form Whisper de Transformers non prouvé] → garde conditionnel : mécanisme natif seulement s'il est vérifié au jalon 0, sinon fenêtres fixes de 30 s.
- [Compilation universelle du verrou torch CPU non vérifiée] → sinon épingler explicitement `torch==2.14.1+cpu` avec l'index CPU dans le `.in`, ou verrous séparés par OS, décidé au jalon 0.
- [faster-whisper 1.2.1 avec huggingface_hub 2.x non prouvé] → aucun téléchargement par faster-whisper (modèle déjà local, D10) ; borne `huggingface-hub<2` dans son verrou si l'import échoue.
- [Pic mémoire cumulatif, non attribuable à un audio précis] → valeur consignée comme pic du processus depuis son démarrage.
- [Durée totale de l'opération incluant décodage et écriture] → ne mesure pas l'inférence seule ; la durée du processus moteur et les temps de chargement/transcription sont consignés séparément.
- [mmap de transcribe.cpp : RSS partiellement composé de pages de fichier] → mode consigné ; option `no_mmap` réglable.
- [transcribe.cpp pré-1.0, ruptures d'API entre versions mineures] → versions épinglées ensemble ; mise à jour = changement explicite.
- [Fenêtres fixes : mots coupés et perte de contexte] → appliquées uniquement aux familles sans mécanisme natif vérifié, durée consignée par audio.
- [Dépôts restreints (acceptation de conditions, jeton absent)] → message explicite d'accès refusé.
- [Débit des modèles lourds sur CPU] → aucune limite imposée ; RTF affiché comme repère.
- [Framework ne couvrant pas les règles locales spécifiques] → hook central testé pour `Host` avec port, `Origin` et jeton par démarrage ; pas de TLS, trafic local uniquement.
- [Serveur de développement activé par facilité] → seul le lancement CLI avec Waitress est documenté et testé, debug/reloader interdits ; pas de serveur Werkzeug en usage normal.
- [Téléchargement non annulable dans le processus serveur] → aucune garantie de délai global de sortie ; attente applicative bornée, marqueurs prêts interdits après passage à l'arrêt, verrou d'instance conservé jusqu'à la fin des accès aux données ou la mort réelle du processus.
- [Signaux et lanceur uv] → sous Linux, Ctrl+C par PTY, double signal (83 signaux ignorés), SIGTERM sur `uv` puis sur le serveur, port occupé, arrêt brutal et absence de survivant sont prouvés par la sonde 1.7 du 2026-11-01, avec la limite d'un PTY automatisé et non d'une console humaine ; sous Windows, la console interactive n'est pas éprouvée et les points vérifiables sans console sont exercés par la suite de tests en CI (D14) ; fermeture brutale traitée par D11.
- [Dépendances web supplémentaires] → Flask et Waitress épinglés, dépendances transitives verrouillées ; mises à jour explicites avec rejeu de la sonde, sans extension préventive.
- [Écriture atomique insuffisante si le disque est plein] → l'erreur est journalisée, l'exécution passe en échec et le JSON précédent reste lisible.
- [Verrou sans hashes et `--find-links` distant] → le verrou Transformers dépend d'une page d'index PyTorch CPU distante et n'est pas figé par empreinte : résolution fragile, acceptée pour le prototype ; `uv pip sync --no-build` et le verrou versionné restent la référence.
- [huggingface_hub différent entre serveur et moteur] → 2.3.0 côté serveur, 2.4.0 en transitive côté moteur Transformers ; écart consigné, à revoir si une API utilisée diffère.
- [« Verrou compilé une fois » inexact] → le seul verrou Transformers a nécessité trois compilations (original, candidat avec `--find-links`, ajout de librosa) ; chaque verrou est compilé et versionné séparément.
- [Dépôt faster-whisper de référence remplacé] → `Systran/faster-whisper-large-v3-turbo` répond 401 ; le dépôt utilisé, validé fonctionnellement, est `dropbox-dash/faster-whisper-large-v3-turbo` (dépôt tiers, sha256 consigné dans le manifeste).
- [Durée native maximale prouvée sur un seul PC] → les 5 min ont été prouvées sur un PC Linux de 30 Gio de RAM (plafond RSS 12 Gio non atteint) ; sur une machine moins dotée en mémoire, le seuil de bascule vers les fenêtres de 30 s reste à revoir. Le mécanisme est commun aux deux OS : aucune règle par OS n'est introduite.
- [Message « Interface disponible » affiché avant l'échec d'écoute sur port occupé (sonde 1.7 Linux)] → limite acceptée : la corriger exigerait `create_server`, écarté par D2 et D5.
- [Image de runner Windows qui évolue] → libellé d'image explicitement versionné et version d'image consignée à chaque run ; une évolution d'image est traitée comme un changement de preuve.
- [Disque du runner Windows de 14 Go partagé avec l'OS] → un seul moteur et un seul modèle par job, jobs indépendants, aucun cache de poids ; un dépassement fait échouer le job et est consigné, jamais contourné.
- [Dépôt public : exposition de l'historique, de la mémoire et des licences] → audit préalable et gate de publication explicite (D15) ; sans audit complet, pas de publication et pas de jobs Windows.
- [CI verte prise pour une garantie de performance] → ressources mesurées consignées comme non représentatives ; le RTF obtenu en CI n'est qu'un contrôle de fonctionnement.
- [Multiplicateur Windows sur dépôt privé] → jobs Windows exécutés après publication ; avant, seul le job Linux de tests est prévu. Ce repli n'est pas décidé.
- [Audio de parole synthétique indisponible sur le runner Windows] → faisabilité vérifiée avant les jobs d'inférence, sans présumer SAPI ni ajouter de dépendance ; à défaut, arbitrage explicite de l'utilisateur, sans remplacement par du bruit ni affaiblissement silencieux du critère de transcription non vide.
- [Options hors ligne prises pour une preuve d'absence de réseau] → les jobs n'exercent que les options hors ligne ; la coupure réseau réelle reste une limite consignée, une sonde CI dédiée pouvant être ajoutée après revue.

## Migration Plan

Nouveau projet, aucune migration. Préalable sur le serveur de développement : installer uv pour l'utilisateur, sans toucher au Python système ni au runtime de Basic Memory ; seules les dépendances du serveur, pile web incluse, y sont installées. Sur les PC : installer uv via l'installeur officiel, puis `uv run transcription-bench`. Aucun moteur ni poids n'est installé sur le serveur de développement.
Pour les vérifications Windows : audit du dépôt (D15), décision explicite de publication, puis ajout du workflow (D14) d'abord en déclenchement manuel, avant tout déclenchement automatique élargi.
